Desktop flow, in the analytics palette

One SVG source below, rendered four times with different highlights. Every instance on this page is a clone of the same markup — editing it once changes all four.

The colour decisions

  • I dropped the green/blue/red entirely. ArchDiagram states its contract in the source: amber is reserved for the lit state, and exactly one object carries a hue at rest — teal, because it's amber's complement, so the resting focal colour never competes with the interaction colour. Three decorative hues would have broken both halves of that.
  • Value descends inward, same as the analytics figure: device shells are the lit surface (#111a21), the herdr and Zed panels are holes cut in them (#0a0f12), and the sandboxes sit back up as raised nodes (#202d37). Depth now does the work the borders were doing alone.
  • GitHub takes the core treatment — teal edge and the same 16px glow the warehouse has. It's the convergence point and the one element that stays meaningful at every step of the walk. If you'd rather the sandbox carry the hue, since the prose calls it "the most important primitive," that's a one-line swap.
  • The lit state adds a 12px amber glow on top of the amber stroke. ArchDiagram gets its highlight from stroke plus dimming everything else to 0.28; the glow is the part you said you liked, so I made it explicit rather than implied.
  • The cross-family arrow is neutral now. It was red. Under the contract it can't have its own hue, so the relationship rests entirely on the prose — the same open question from last round, now with one fewer way to solve it.

Yes — one source, every instance

This page proves it the crude way: the SVG lives in a <template> and a few lines of script clone it into each slot. In the post it needs no script at all — it's a component prop, resolved at build. 

---
// src/components/StackDiagram.astro
interface Props { highlight?: string | string[] }
const { highlight = [] } = Astro.props;
const lit = new Set(Array.isArray(highlight) ? highlight : [highlight]);
const grp = (k: string) => (lit.has(k) ? 'grp lit' : 'grp');
---
<svg class:list={['stack', lit.size && 'engaged']} viewBox="0 0 900 540">
  <g class={grp('macbook')} data-key="macbook">…</g>
  <g class={grp('herdr')}   data-key="herdr">…</g>
  <g class={grp('sandbox')} data-key="sandbox">…</g>
  …
</svg>

Then the post's five figure slots become five lines:

<StackDiagram />
<StackDiagram highlight="sandbox" />
<StackDiagram highlight="herdr" />
<StackDiagram highlight="zed" />
<StackDiagram highlight={['phone', 'hub']} />
  • Geometry, palette and copy live in exactly one file. Move a box, rename a node, change the amber — all five instances follow. Adding a sixth appearance costs one line.
  • The keys are the API. macbook, herdr, sandbox, zed, phone, hub. Groups are siblings rather than nested so any combination can light independently — lighting sandbox doesn't drag herdr along.
  • Each path travels with its source. The riser to the hub is inside the group it leaves from, so highlighting herdr also highlights herdr's route to GitHub. That falls out of the grouping rather than needing its own key.
  • One thing to fix on the move: marker ids are document-global. Five instances means five #ah definitions and every url(#ah) resolving to the first — harmless while they're identical, but it breaks the moment one instance differs. Either suffix the ids per instance or hoist a single <defs> into the layout. ArchDiagram already prefixes its markers for this reason.
