## Thesis

Your expert attention is the most valuable resource when building with agents. When you could build anything fast, what actually gets built? Balancing product work and improving my tools in parallel gives me the best throughput. My set of tools is ever evolving, but the foundation is to maximize speed with tightly scoped work in tighly scoped enviornments. I demand productivity and focus from my agents by restricting their access to only what is needed. My agents write code, commit, push, open PRs, and request outside reviews unattended, all because they have access to everything they need and nothing more. My time and attention is spent making real decisions and shipping, not mindlessly orchestrating.

## What wasn't working

I love Zed so much, its a popular tool for multi-plexing across agents for good reason. I love using it to write and inspect code myself, but an agent-centric workflow uses different screenspace than a code-centric workflow. Carefully toggling back and forth became a tiresome chore. Plus I'd leave the house and my whole high velocity multi-agent workflow is stuck to my macbook while I was doing nothing on the train on way to somewhere else. The solution was to split the two workflows into two tools: I still use Zed to write and inspect code myself, and I use Herdr for herding agents.

## The stack

{/* FIGURE: the layer diagram — laptop → VPN → ssh → herdr → sbx-new → agent → skills → subagents → GitHub. */}

My dev stack for agents keeps them each in their own Docker sbx sandbox. The tool is specifically for agents building a microVM for each and has great features like like credential substitution in the network proxy. What's in these sandboxes is determined by Docker sbx kits and what they can reach is determined by an sbx network policy. Where I deviate from their operational model is that I make these environments ephemeral by construction. sbx gives you the tools to make them each a special snowflake, but state management is complex and annoying so I choose to eliminate it when I can.

When spinning up sandboxes you have many choices to make. Each choice is very personal to each developer and organization and should be codified in an auditable way. I've concentrated all of the decisions that make up my security risk profile into a tool I wrote with the uninspiring name `sbx-new`. I'm not going to share it because I chose to collapse all the structure that would be required to express multiple people's security profiles and instead simply express what I am comfortable with. The transferable part is not the tool itself. It's that the tolerances live in one place, enforced by construction, instead of scattered across prompts, doc comments, and good intentions.

`sbx-new` has several jobs:
- Agent support: I use both claude and codex but will likely add more.
- Toolchain provisioning: Done via a versioned pre-built image.
- Coworking model: A fresh clone for branching.
- Permissions: Check for the repo-scoped GitHub deploy key, or print the one step command to make one.
- Hooks: Anything you want to provide it from the outside. I provide it with Herdr status hooks, and a pathway to request a cross-family review.
- Cleanup: sbx microVMs are cheap and I drop them quickly. Every invocation cleans up old unused ones on a background thread.

These definitions grow and change over time. For example, I've been doing an unusual amount of front end work lately and decided to throw playwrite and chromium into the base image. The more I work, the more the tools change to reflect my needs.

This creates the most important primitive of the whole workflow: One disposable environment per task.

Each agent's sandbox is launched inside the Herdr UI. What makes Herdr so appealing is that it has a minimal ui footprint that lets your terminal tabs span multiple workspaces while detecting and displaying the status of each agent you've launched. The layout is designed for both desktop layouts _and_ mobile layouts.

With Zed in it's own Mac workspace, I pull what the agent pushes, test, make changes and push back. It feels extremely familiar since this is how I've always worked with collaborators. I can have multiple agents from different families work on the same branch or on different branches all while clearly visible in the Herdr UI.

# When I leave the house

With this construction it's safe to let agents work when you're not at the keyboard. That doesn't mean you should be producing maxiumum value when on dinner dates or while watching a movie. But when I'm in a waiting room or on a bus I'm usually mindlessly scrolling to pass the time. I'd much rather be building something in that time and I bet some of you would too.

When I leave the house, I turn on caffeine, shut off the screen and walk out the door. I have Ubiquiti equipment at home so I can use [UniFi](https://ui.com/) Teleport to make my local network accessible to my phone. If you don't, Tailscale works just as well. I open up Termux, ssh into my laptop, type `herdr` and the whole herd is ready for me to take action. Between Herdr over ssh and the Github app I can do pretty much everything I can at home. The changes I might have pushed myself, I'll just ask the agent to do for me.

Unfortunately ssh isn't the most resilient to faulty networks, so I was hoping to fold [`mosh`](https://mosh.org) into the stack to protect against unnecessary disconnects. Unfortunately, until [this issue](https://github.com/mobile-shell/mosh/issues/1364) is resolved I'll have to live with occassional disconnections. In practice on my outings I get maybe one disconnect an hour which is tolerable.

## Watching six things at once

Here's how this usually goes: I sit down with one or two big ideas I want to implement. Maybe write a new blog post on my AI workflow and add a new graph to my personal analytics BI that shows how many commits I've used agents for over time. Analytics I split up into "Add personal GitHub commits as a source" and "model commits by agent or human author over time through to BI." The blog post I split into a research task and a collaborative outline creation. Now I have two workstreams with blocking and subsequent tasks which is easy to keep in my head. I fire the first two off, and I realize TODO what dotfiles do I kick off??

- One to six concurrent agents, most commonly three.
- Supervision is not watching code scroll by. It is: making decisions at human gates, answering questions, and choosing which threads to continue and which to kill.
- `herdr` is where work is supervised. GitHub is where it's resolved. Final coordination — merging — happens in the GitHub UI, not the terminal.
- The integration problem worth describing: the agent doesn't run in the pane, it runs inside a VM. Without a bridge, herdr sees a pane running a sandbox and has no idea whether the agent inside is blocked on a question.
  - The fix is a hook inside the sandbox writing state to a directory bind-mounted at the identical path on both sides, plus a watcher on the host that translates it.
  - It's a complete no-op outside a herdr pane. Optional layers have to be true no-ops or they become mandatory by accident.

## The session follows you

{/* Second spine. Frame as reclaiming time, not as being on call. */}

- [Termux](https://termux.dev) → ssh → herdr from the phone. Because the sessions live on the laptop, walking in the door and sitting down resumes the exact same panes. Mobile isn't a second workflow; it's the same one, continued.
- The real argument: I don't want to plan my gym trip around when my usage window resets. Downtime — a waiting room, a train, the ten minutes before something starts — is time I was already going to spend on my phone. Fiddling on your phone during down time is not something AI companies invented. I'd just rather spend it moving my work forward than scrolling.
- Most real work still happens at the laptop. The phone covers the in-between.
- What actually breaks, and it isn't "AI is hard" — it's a mouse-mode negotiation bug three layers down:
  - [`mosh`](https://mosh.org) would give me roaming and resumption over a flaky mobile link. I can't use it.
  - Zellij-style clients request mutually exclusive mouse modes in ascending order of preference, relying on emulators to ignore what they don't support and stay put. mosh instead disables the previous mode and stores only the most recent.
  - Termux doesn't support any-event mode. So the request goes through, mosh turns off the working mode, Termux won't honor the new one, and all mouse reporting dies. Terminal.app is fine — it supports the mode.
  - I filed [a confirmation upstream](https://github.com/mobile-shell/mosh/issues/1364) and live with plain ssh. It drops once or twice on a typical outing; herdr's detach/reattach absorbs most of it.

## The loop

{/* /dev-workflow. Stage-by-stage but compressed — the gate and the kills are the parts that matter. */}

- Invoked explicitly. It never fires on an ordinary coding request.
- **Setup.** Detect the real base branch. Open a GitHub issue titled with the run ID — that issue is the run's durable log. Clone the base into a temp standalone clone on a `wip/` branch. Run state goes in the local exclude, never `.gitignore`, so it can't pollute the diff.
- **Design.** A designer subagent writes a design doc, then a critic loop: a reviewer appends a structured verdict to a journal, a reviser makes surgical edits on `blocking`. Capped rounds, journal compacted partway through.
- **The human gate.** The one place human judgment is mandatory. I see the summary and the open questions in chat — I never open a file in a temp clone to approve something.
  - Small tasks: rarely bites. Anything bigger: almost always two to five rounds of feedback before I approve.
  - That number is the argument for putting the only mandatory gate at design rather than at code review. Feedback on a design costs a paragraph. The same correction after implementation costs a rewrite.
- **Where runs die, and why that's the payoff.** Killing a thread is normal supervision, and it almost always happens at or right after design — before any code exists.
  - The design work found a hard blocker; an API simply can't do the thing.
  - The premise wasn't well founded.
  - The task is really blocked behind tech debt, so the run gets shelved, the debt becomes its own run, and the original comes back after.
  - Reframe: design isn't only a quality filter on *how* something gets built. It's a cheap discovery mechanism for *whether* it should be. Ten minutes of agent time to establish "the API can't do this" is a bargain, and it's the strongest counter to the idea that agent workflows are just about typing faster.
- **Plan.** Same critic loop, no human gate. Deliberate — design is where my input changes the outcome; the plan stage exists to iron out detail.
- **Implementation.** An implementor writes code, commits, and runs the repo's quality gate. Then the orchestrator enforces a contract on every exit: working tree clean, gate results present, and the gate's timestamp not older than the last commit — it has to have actually run after the final change. Violations trigger a bounded respawn with a specific correction.
  - Efficiency detail worth including: the implementor stays warm across fix rounds rather than being respawned cold, because a cold start re-reads the plan and re-explores the codebase every time. That's the dominant avoidable cost of the loop.
- **History rewrite.** The messy trail gets squashed into a handful of clean, well-titled commits before review. Readable history is written before anyone reads it, not after.
- **PR.** Push, open with `Closes #<issue>`, post a recap: rounds and verdict per stage, which model reviewed what, how many commits.
- **On scoping, which is not a workflow thing.** I don't size tasks to fit a run. I size them the way you're supposed to size any commit: a small, iterable chunk that makes real progress on its own. Standard engineering.
  - It just turns out that a well-defined chunk of that shape takes twenty to sixty minutes here. That's an observation about the work, not a target I aim at.
  - A poorly defined one doesn't take longer — it spins off the other work that had to happen first. That work gets done, then the original comes back and finishes normally.
  - This is why three concurrent agents is manageable, and it's the same mechanism as the kills above, seen from the other side.

### The mechanisms that make it trustworthy

- **The GitHub issue is the state store.** Design and plan are posted as issue comments with markers. Resume reads which markers exist, infers the stage, and reconstructs the artifacts — it can even re-clone the branch if the temp clone is gone. No database, no checkpoint files. Just artifacts a human can read.
- **Anti-sycophancy.** A reviewer can't approve without enumerating at least one specific, falsifiable objection it checked for and found absent or resolved. An approval with an empty considered-section is malformed and gets respawned. The prompt discourages rubber-stamping; the orchestrator validates that it did.
- **Boundary crossings.** If a change touches serialization, FFI, IPC, a worker, or the network, green unit tests are explicitly declared insufficient — the reviewer has to look for a test that exercises the real boundary.
- **Post-validation over trust.** Every subagent's output is structurally checked. Malformed output means a respawn with an exact correction, and it doesn't consume a round. Prompts set intent; the harness enforces it.
- **Escalate, don't guess.** Every loop has a round cap. On exhaustion it stops and asks me, showing what's unresolved.

## Two model families, on purpose

- Both Claude and Codex do primary work, genuinely alternating. Claude runs until its usage window saturates, then work shifts. Each serves as the cross-reviewer for the other.
- Before the PR, the diff gets read by the other family — an independent, read-only second opinion, up to a few rounds. Blocking findings go back to the implementor.
- It earns its keep: nearly every run turns up something.
  - The effect is strongest at near-parity with different results. Codex 5.6 against Opus 4.8 were close in quality and consistently disagreed in useful ways. When one family is clearly ahead the exchange is less symmetric, but the second pass still catches things.
  - This is a better argument than the usual ensemble hand-wave: near-parity plus different failure modes is what makes a second opinion worth anything. Two instances of the same model mostly agree with themselves.
- Safeguards, because I'm handing my working tree to another vendor's agent:
  - Read-only where supported, but the guaranteed protection is a worktree-integrity check after every invocation — if the sibling touched anything, hard reset and warn.
  - The stage never blocks the run. On any failure it logs why, warns loudly, and continues.
  - (Optional color: the verdict parser had to take the *last* sentinel pair, because `codex exec` echoes its own prompt back to stdout.)
- **What it costs.** Two Pro plans ran this whole flow, and ran it well. That's about forty dollars a month for what the workflow was already giving me, which is extremely modest. I only recently moved up to Max 200. Worth saying plainly, because the setup reads more expensive than it is.

## Auth is an integration constraint now

{/* The Gemini beat. Make the general argument, not a vendor complaint. */}

- I cancelled Gemini Pro because I couldn't integrate the CLI. The interesting part is *why*, and it isn't model quality.
- It works fine with an API key. The problem is subscription auth: it needs a browser login, which doesn't work headlessly in a sandbox — and would have to be redone on every launch.
- (Optional, one line, only to keep two separate things straight for readers who follow this: the other well-known Antigravity gap is [no ACP mode](https://github.com/google-antigravity/antigravity-cli/issues/31), which killed it as a [Zed](https://github.com/zed-industries/agent-client-protocol) agent. That's orthogonal here — this workflow never speaks ACP, it shells out directly.)
- A workflow whose whole premise is a fresh disposable VM per task cannot absorb a per-launch interactive browser handshake. That's not an inconvenience, it's a structural mismatch.
- Compare what works: Claude's subscription OAuth state is captured once on the host and reused by every later sandbox. Same for the OpenAI secret. The requirement isn't a protocol — it's auth state that can be captured once and injected into a fresh machine.
- The general point, and the one I'd want a reader to take away: as disposable agent environments become normal, *how a vendor lets you authenticate becomes a first-class integration constraint* — as important as model quality. A browser-only login is soft lock-in to long-lived, hand-configured machines.

## GitHub is the interface

- One issue per run, one PR per change, reviews signed with the model that wrote them so cross-model review is visible in the conversation.
- The strategic point: GitHub is deliberately the coordination surface, not the tooling. A collaborator can run a completely different setup — different editor, different agent, no agent at all — and this workflow never has to know.
- Forcing tool uniformity is the failure mode. A shared artifact layer is the fix, and it's the only thing that works across company boundaries.
- Narrative spine worth using: the dotfiles repo is developed *with* this workflow. Its history is full of merges from its own `wip/dev-workflow-<id>` branches. The workflow builds and improves itself.

## What running agents taught me about my own hygiene

- No incident. But I had to rotate several API keys, because of how aggressively agents grep through a filesystem.
- The response wasn't to clamp down on the agents. It was to fix the underlying bad practice: every key now lives in the macOS keyring, none in plaintext `.env` files — the way it always should have been, and the way most developers still don't do it.
- The line to land: the agent didn't create the exposure, it revealed it. Running agents on your machine is an honest audit of your own secret hygiene.

## What this costs

{/* Same register as the warehouse post — name the limits plainly, don't soften them. */}

- **One machine, one point of failure.** All of it hangs off a laptop left awake at home. Lid closed, power blip, or ISP down and there is no workflow at all.
- **The tools are never finished.** But this isn't months of yak-shaving before you get to work — it's closer to an artisan sharpening tools. I make small changes nearly every day and the tooling keeps up with me. The workflow itself is what makes that sustainable: improving it is just another task that goes through it.
- **Termux on Android is not a graceful experience.** It's the price of the thing I actually want.
- **The nicer mobile UX costs the thing I value most.** Running it all on Max 200 with dispatch is a much better phone experience — and it breaks the two-pane, multi-agent shape that is the entire reason this works. I keep the rougher path on purpose.

## Closing

- Restate the spine: less access, more output. The isolation is what let me stop supervising and start managing.
- Note honestly that everything quantitative here is my experience, not measurement.
- The workflow only recently started recording per-stage rounds, verdicts, models, and durations. There isn't enough history yet to say anything real. When there is, that's the follow-up post — and "here is measured data from N runs of my own agent workflow" is a claim almost nobody in this genre can make.
