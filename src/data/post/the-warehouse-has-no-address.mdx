This is a single-person analytics pipeline: a few third-party APIs in, a DuckDB warehouse, dbt on top, a dashboard on the far side. The standard shape, and the sources barely matter — swap them for whatever you care about. The one unusual decision is that **the warehouse is not a service**. It is a file, and nothing can reach it.

Twice a day a container starts, mounts that file, loads the sources, runs dbt, bakes five small JSON extracts, ships them to a static host, and exits. Start to finish it takes about a minute. The rest of the day — all twenty-three hours and fifty-eight minutes of it — nothing is running at all. What is public is a folder of files behind an auth check; what is private has no port, no connection string, and no credentials to rotate.

The point is not elegance for its own sake. It is that **I maintain this alone, in whatever time is left over**. Every live endpoint is something to monitor, patch, and be woken up by. This design has none of mine to run.

## What this costs

**Freshness is bounded by the schedule.** Data is at most twelve hours old, and older if a source is down. The dashboard reports its own freshness rather than hiding it. If you need minutes, this is the wrong design and no amount of tuning fixes that.

**The published side cannot ask new questions.** It holds answers, not a database. A new question means a new dbt model, a new loader, and the next run — not a filter in a UI. In exchange, no query I write can be slow for a reader, and no reader can write a query at all.

**One writer, by construction.** One file, one process at a time. That is free correctness for one person and the first thing that breaks the day a second person needs to write. It is a deliberate ceiling, not an oversight.

**Recovery is only as good as the restore.** A backup that has never been restored is a guess. `restore-test` pulls the latest snapshot into a scratch directory and reads every Parquet file back. It is treated as a gate before anything irreversible, not as a nicety.

## Where each role went, and why that one

The second column of each card is deliberately empty. Every choice here is load-bearing for one person with limited time, and the honest boundaries of that are mine to write down.

<RoleTable>

<Role role="Warehouse" choice="DuckDB">

A file, not a service. Between jobs there is nothing to run, secure, or upgrade — the entire operational surface of the database is a path on disk.

</Role>

<Role role="Compute" choice="Railway cron job">

A native scheduled job with a volume it can mount. No resident worker, no health check, no domain. Overlapping runs are skipped by the platform.

</Role>

<Role role="Load" choice="Node.js">

One small module per source, each owning its own table. Creating the database, schemas, and tables is the loader's job, so adding a source never means hand-migrating warehouse state.

</Role>

<Role role="Model" choice="dbt-core + dbt-duckdb">

Ordinary staging → intermediate → marts modelling with tests, pointed at a local file instead of a cluster. Nothing about dbt requires a warehouse that listens.

</Role>

<Role role="Extract" choice="Observable Framework">

Its build-time data loaders are the whole trick: each one runs a query during the build and writes a static file. That is what turns a warehouse into a website with no database behind it.

</Role>

<Role role="Hosting" choice="Netlify">

Serves a directory. The only thing it has to do well is stay up, and it is not my process if it doesn't.

</Role>

<Role role="Auth" choice="Clerk">

Session handling is the one thing worth not writing myself. It runs in an edge function ahead of every path, and it is the only server-side logic in the system.

</Role>

<Role role="Durability" choice="restic → Backblaze B2">

Client-side AES-256 before anything leaves the machine, because provider-side encryption alone is not enough for data this personal. B2 over its S3-compatible API, which restic recommends over its native backend.

</Role>

</RoleTable>
